# CODEX / BLENDER — complete Jurassic Domination creature art pipeline overhaul

You are a senior character artist, technical artist, rigging specialist and Three.js engineer. Work in the local Jurassic Domination repository. **ACTUALLY EXECUTE** the changes; do not stop at a plan or make cosmetic shader-only tweaks.

First read `references/dinosaur_reference_catalog.csv` and `references/visual_reference_catalog.md`, then inspect `src/data.js`, `src/content.js`, `src/creatures.js`, `src/renderer.js`, existing `assets/models/` and the current rendering/animation architecture. The reference catalog includes **all 102 creature IDs**, including dinosaurs, non-dinosaur prehistoric animals, mythical animals, and special bloodlines. Do not omit any real dinosaur or accidentally treat non-dinosaurs as dinosaurs.

## The art direction and quality bar
Create original high-quality, **semi-realistic prehistoric character art**: compelling recognizable silhouettes, anatomically appropriate skulls/limbs/tails, readable proportions, naturalistic scales, feathers, bony plating and skin folds, grounded earth-toned palettes with deliberate accent patterns, polished PBR maps and strong silhouette legibility at the actual game camera distance. Models should look like individually designed believable creatures, not recolored spheres/cones/lofted tubes or generic T. rex shapes. Follow the reference images for **anatomy and shape**, not exact pose, color, or copyrighted styling. For uncertain reconstructions (e.g. Spinosaurus) choose a defensible interpretation and document it.

## Make Blender integration real
1. Confirm Blender is installed and can open a .blend file or run via its Python CLI; verify Blender MCP access independently, including the listener/port and a successful real operation. If MCP is unavailable, use `blender -b --python <script>` where Blender is accessible. Never claim Blender was used unless the actual blend/output files exist.
2. Build reproducible Blender Python scripts and native .blend sources for each creature, stored in a clearly structured asset directory. Use actual sculpt/retopology-friendly topology where possible, controlled loops for anatomy, UVs and texture baking, game-ready shading and well-defined articulation. Avoid a 'primitive assembly' look, detached limbs, intersecting chunks, flat-color blobs, hard balloon forms, impossible joints and stretched UVs.
3. Build and **review ONE first-class Tyrannosaurus rex model** to establish the standard. Render full-body front, side, three-quarter and top views with neutral studio lighting; inspect silhouette, anatomy, materials and face. Refine it until clearly better than the existing procedural mesh. Then apply the same quality gate to the remaining catalog without merely cloning the rex.
4. Use the primary image link for each species. For `reference image gallery` links, browse and choose a credible life restoration with full-body proportions and corroborate with a second source. If internet access is unavailable, mark it as an unresolved reference; do not hallucinate having seen an image. For variants reuse the base species' underlying skeleton/rig and upgrade the skin, armor, attachments, special VFX.
5. Handle small feathered theropods, large theropods, ceratopsians, stegosaurs, ankylosaurs, ornithopods, sauropods, pterosaurs, crocodyliforms, serpents, plesiosaurs/pliosaurs and fantasy beasts **as genuinely different anatomies**. Create shared rig families only where biologically sensible. Especially: proper four-winged Microraptor; feathers/sickle claws for raptors; Dimetrodon is not a dinosaur; pterosaur wings are skin membranes; marine beasts get four flippers, not legs.
6. For each model produce a production-ready `.blend` plus `.glb` export with clean pivots, correct scale/up axis, embedded or referenced PBR textures, armature weights, LOD strategy, transparent-material handling for feathers/wings, eye/jaw articulation, and practical locomotion/idle/attack/hit/death motions. Reuse relevant animations carefully and ensure actual exported animations are present. Do not silently substitute a static unrigged mesh.

## Integrate into the actual game
7. The game is Electron + Three.js, and `src/creatures.js` currently constructs procedural THREE.Group geometries. Inspect current loading paths; implement or fix a robust `GLTFLoader`-based cache/loader and species-ID-to-GLB manifest **if it is not already present**. Use asynchronous preloading, one shared immutable source asset per species, instances/clones as appropriate for skinned models, and fallback to old procedural models on a failed load. Preserve the required `createDinosaur`/`animateCreature` behavior and existing species state/attacks; update animation bridging for rigged GLBs and gameplay growth/color genetics/cosmetic variants. Prevent orphaned GPU resources and duplicate downloads.
8. Test each new model at actual gameplay scale and camera height/distance in all key biomes, daylight/night/storm conditions, sanctuary, evolution previews and the 3D encyclopedia. Correct clipping, floating feet, too-large/tiny heads, faces unseen from top-down camera, incorrect shadows, missing textures, wrong forward direction and unrealistic movement. Provide screenshot comparison of old/new in gameplay (not only Blender renders).
9. Preserve FPS and memory with LOD, texture atlases/appropriate resolutions, culling, texture compression where supported, restrained bone counts and asset budgets. Do not add costly subdivisions or large opaque feather cards to every background animal.

Keep all **102** species IDs working and make model coverage explicit in an automated audit with pass/fail status, files, dimensions, UV validation, animations, screenshot links, reference URL and license notes. Include progress output and verification commands. Run project build and applicable tests (including visual QA where supported), fix regressions. Do not fabricate test or screenshot results.
